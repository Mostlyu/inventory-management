Reusable Playbook · FIAE

Building a PHP · MariaDB · Docker CRUD App

A step-by-step method for building a small, maintainable web app from nothing — the same path used for the inventory project, written so you can repeat it on any similar project, on your own.

The one rule that governs everything

Design before you code. Most of this playbook happens before you write a single line of application logic. Rushing to code produces something that runs but can't be changed. The order below — understand → model → draw → structure → build — is the whole discipline.

01Set up the environment with Docker

Goal: a local, reproducible environment you can throw away and rebuild in seconds, without installing PHP/MySQL on your actual machine.

The mental model you need first

TermWhat it isAnalogy
ImageRead-only blueprint of an environmentA class / a recipe
ContainerA running instance of an image (disposable!)An object / a cooked meal
VolumeStorage that survives a container's deathA filing cabinet
ServiceOne entry under services: — something that runs—

How to do it

  1. List the services you actually need. Test: does it run and stay running? For a PHP+DB app that's three — a database (MariaDB), the app (PHP+Apache), and a DB admin GUI (Adminer). A volume or Dockerfile is not a service.
  2. Write docker-compose.yaml with two top-level keys, services: and volumes: (siblings — indentation matters).
  3. Persist the database with a named volume mounted at the DB's data dir (/var/lib/mysql for MariaDB). Without it, docker compose down wipes your data.
  4. Bring it up: docker compose up, then watch the logs for each service's "ready" line.
services:
  db:
    image: mariadb
    environment:
      MARIADB_ROOT_PASSWORD: example   # required
      MARIADB_DATABASE: mydb           # auto-creates a database
    volumes:
      - db_data:/var/lib/mysql
      - ./db:/docker-entrypoint-initdb.d   # runs *.sql on first init
  app:
    build: .                # your Dockerfile
    ports: ["8000:80"]      # HOST:CONTAINER
    volumes: ["./:/var/www/html"]
    env_file: [.env]
    depends_on: [db]
  adminer:
    image: adminer
    ports: ["8080:8080"]
volumes:
  db_data:                  # declares the named volume

The single most important Docker idea

Containers reach each other by service name, never localhost. Inside a container, localhost means "this same container." So your PHP connects to the DB at host db (the service name), not localhost.

Gotchas

  • Indentation = structure. A misplaced volumes: or build: becomes a phantom "service."
  • Env vars apply only on FIRST init. MariaDB reads MARIADB_* once, when the volume is empty. To change the password/db later you must docker compose down -v (which wipes data).
  • depends_on waits for the DB container to start, not to be ready for connections.

02Analyse the domain (no code yet)

Goal: understand what you're building and for whom, before touching tables or code.

  1. One plain-language paragraph: what does the system do, and for whom? No tech words.
  2. Find the entities. For each candidate noun ask: is this something the business cares about on its own, or just a property of something else? On-its-own → entity (a table). Property → attribute (a column). Beware the trap "it relates to X, so it's an attribute" — almost everything relates to something.
  3. Write the processes as user stories: Als [Rolle] möchte ich [Aktion], damit [Nutzen]. The Nutzen must be real business value, not a restatement of the action.
  4. Write the business rules: the invariants (e.g. "stock can't go negative", "every item needs a category", "can't delete a category that still has items"). Each becomes a constraint or a validation later.

Checkpoint

Can you justify each entity's existence in one sentence? If not, it's probably an attribute.

03Model the data

Goal: turn the analysis into a solid relational schema.

  • Primary keys: prefer a surrogate id (auto-increment). It never changes, so other tables can safely reference it forever — natural keys (SKU, name) leak into every table when they change.
  • Foreign keys go on the "many" side of a 1:n. One category → many items, so category_id lives on items. (A single column can't point at many rows, so it physically can't go on the "one" side.)
  • ENUM vs lookup table: use an ENUM for a small, fixed set with no own data (e.g. movement type: in/out). Use a lookup table when it has its own attributes or users manage it at runtime (e.g. categories).
  • Store vs derive a computed value (like current stock): deriving from history (SUM) trades a little read speed for a number that can never disagree with itself. Storing it is faster to read but must be kept in sync on every write — the classic source of silently-wrong data.
  • Constraints turn business rules into DB rules: NOT NULL, UNIQUE, CHECK, and FK ON DELETE RESTRICT/CASCADE/SET NULL.
-- derived current stock for one item:
SELECT COALESCE(SUM(
         CASE WHEN type='in' THEN quantity ELSE -quantity END
       ), 0) AS current_stock
FROM stock_movements
WHERE item_id = ?;

Gotchas

  • CHECK (x > 0) does not reject NULL (NULL comparisons are UNKNOWN, which passes). Add NOT NULL too.
  • Column definition order: type NOT NULL CHECK(...) — attributes before the CHECK.
  • Save the schema as a committed schema.sql; don't click tables together by hand.

04Draw it (UML)

Goal: model visually before coding. Text-based tools (Mermaid) keep diagrams in the repo as code.

DiagramAnswers
ER-DiagramTables, keys, relationships (must match schema.sql)
Use CaseWhich actors can do what, at the system boundary
Class / DomainThe objects your code will become — data + behaviour
ActivityThe steps of one process; decisions (diamonds) = business rules

Two naming worlds

Tables are snake_case plural (stock_movements); classes are PascalCase singular (StockMovement). Keep them distinct.

Checkpoint

Could a stranger read your diagrams and correctly guess what the app does — with no explanation?

05Structure the PHP (layers)

Goal: not "it runs" but "it's maintainable." One job per layer — Separation of Concerns.

Browser → /public → Controller → Repository → Model → Template → back to browser
                         ↑ /config + .env (settings & secrets)
LayerOne job
/publicThe only web-reachable folder; index.php is the single entry point
/src/ControllerCoordinates one request (calls repo, picks template) — no SQL, no HTML
/src/RepositoryAll SQL lives here
/src/ModelDomain objects (data + behaviour)
/templatesHTML views
/config + .envSettings and secrets, read once, used everywhere

How to do it

  1. Secrets in .env (host, db, user, password), listed in .gitignore. Never hardcode or commit secrets. Load into the container via Compose env_file:, read with getenv().
  2. One reusable DB connection (a Database class). Single source of truth: change the password in one place. Configure PDO with ERRMODE_EXCEPTION (errors throw) and FETCH_ASSOC.
  3. PSR-4 autoloading via Composer: map a namespace prefix to src/ in composer.json, run composer dump-autoload, then one require vendor/autoload.php replaces every manual class require.
  4. Point Apache's DocumentRoot at /public so /src, /config, and .env are unreachable by browser.
# composer.json
{ "autoload": { "psr-4": { "App\\": "src/" } } }

# generate the autoloader (no local PHP needed):
docker run --rm -v "$(pwd)":/app composer dump-autoload

Namespaces, demystified

App\ is not a folder — it's a nickname that composer.json maps to src/. So App\Model\Category → src/Model/Category.php. use just imports a class so you can write its short name. Inside a namespaced file, built-in classes need a leading backslash (\PDO) or a use PDO; import.

06Build the MVP — one vertical slice at a time

Goal: a first working release. Build one feature through every layer before spreading out.

How to do it

  1. Pick the thinnest slice that proves the idea (e.g. "list categories"). Build Model → Repository → Controller → Template → wire into index.php, end to end.
  2. Follow the data flow one direction only: the Controller fetches data and passes it to the Template. A Template never fetches its own data or calls a Controller.
  3. Add features in dependency order: you can't book a movement for an item that can't be created yet.
  4. For any query with user input, use prepared statements — INSERT ... VALUES (?, ?) with bound params. Never concatenate input into SQL (SQL-injection).
  5. Escape output with htmlspecialchars() when printing user data into HTML (XSS).
// the flow, in five files:
public/index.php     →  new CategoryController()->index();
Controller/…         →  $repo->findAll();  require template;
Repository/…         →  SELECT … → new Category($row…);
Model/Category.php   →  the object (constructor property promotion)
templates/…          →  foreach ($categories as $c) echo htmlspecialchars($c->name);

Discipline

Resist extras. Every "nice to have" goes on a later list. Scope creep is the enemy of a finished MVP.

07Validate & handle errors

Goal: go from "works when used correctly" to "holds up when used incorrectly." Mindset: try to break your own app.

  • Prepared statements everywhere — every query touching user input uses ? placeholders + bound values. Never concatenate input into SQL.
  • Validate on the server, not the client. HTML required is a convenience for real users; anyone can bypass it (a curl request skips the browser entirely). The controller must re-check before writing.
  • Enforce business rules where they can actually be guaranteed. A rule over a single column can be a DB CHECK; a rule over a derived value (like "stock can't go negative", computed from a SUM) belongs in the app, before the insert.
  • Fail gracefully. Catch the errors you expect (e.g. a duplicate on a UNIQUE column → SQLSTATE 23000) and turn them into a friendly message; re-throw the unexpected ones instead of silently swallowing them. A raw DB error should never reach the browser.

Escaping is context-specific

Match the escaper to the output: htmlspecialchars() for HTML, prepared statements for SQL, fputcsv() for CSV. Using the wrong one (or none) is where bugs and vulnerabilities live.

Don't leak which failed

On login, show one generic "invalid username or password" for both "no such user" and "wrong password" — separate messages let an attacker enumerate valid usernames.

08Extend it — one mini-loop at a time

Goal: add value on a solid base. Pick by value, not by fun. Each extension is its own small run of Analyse → Model → Repository → Controller → Template → test.

Search & filter

  • Build a dynamic WHERE: collect only the conditions the user actually supplied, implode(" AND ", ...), and pass a matching params array to a prepared statement.
  • Match the pattern to the field: LIKE '%term%' for fuzzy text (a name); = ? exact for a precise unique code (a SKU).
  • GET, not POST — searching reads data, so it should be repeatable and bookmarkable. On a query-param router, a GET form needs the route as a hidden field (<input type="hidden" name="action" ...>) since GET rebuilds the whole query string.

Authentication & roles

  • Never store plaintext passwords. password_hash($pw, PASSWORD_DEFAULT) stores a one-way, salted hash (so the same password yields a different hash each time); password_verify($pw, $hash) checks a login without ever un-scrambling it.
  • Sessions remember the logged-in user across stateless requests: session_start() at the very top of the entry point (before any output), identity kept in $_SESSION (id, username, role — never the hash).
  • Two gates, both in the router (the single choke point): authentication ("logged in at all?") then authorization ("allowed to do this?"). Enforce on the server — hiding a button is UX, not security.
  • Least privilege: a role column defaults to the lowest-privilege value, so a mistake fails safe.

File export (CSV)

  • A controller action can return a file instead of HTML: set Content-Type and Content-Disposition: attachment; filename=... headers (before any output), write rows with fputcsv() to php://output, then exit — no template.

The real Phase-8 skill: judgment

Deciding what not to build is part of the work. Cutting a feature that doesn't earn its place is as valid as adding one — a smaller, coherent app beats a bloated one.

09Reference

Docker commands

docker compose up -d            # start detached
docker compose down            # stop (data survives)
docker compose down -v         # stop AND wipe volumes (deletes data)
docker compose up --build      # rebuild image after Dockerfile change
docker compose ps              # list services
docker compose logs -f db      # follow one service's logs
docker compose exec db bash    # shell inside a container

The reusable loop for every new feature

Analyse → Model → Repository (SQL) → Controller (coordinate) → Template (display) → test. Each extension is its own mini run of the whole thing.

Collected gotchas

  • Use the service name as DB host, never localhost.
  • DB env vars only apply on a fresh volume (down -v to reset).
  • CHECK doesn't reject NULL — pair it with NOT NULL.
  • Inside a namespace, PDO means App\PDO — use \PDO or use PDO;.
  • A Template receives data; it never fetches it.
  • Point Apache at /public so secrets stay out of the web root.
  • Validate on the server; the browser's required is bypassable.
  • Store password hashes, never plaintext; show one generic login error.
  • session_start() must run before any output.
  • A GET form rebuilds the whole query string — carry the route as a hidden field.
  • Match the escaper to the output: HTML → htmlspecialchars, SQL → prepared, CSV → fputcsv.
