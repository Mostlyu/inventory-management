Inventory Management — Präsentations-Spickzettel

Strategie: Kurz demonstrieren, dass es läuft — dann die meiste Zeit auf das Warum: die Analyse vor dem Code und 2–3 begründete Entscheidungen. Die App ist der Beweis, die Begründung ist die Präsentation.

1 · Live-Demo ~2 min

  • Kategorie anlegen → Artikel darin anlegen
  • Wareneingang 100, Warenausgang 30 → Bestand 70
  • Ausgang > Bestand versuchen → wird abgelehnt
  • Als lager einloggen → Anlegen ist gesperrt

Ich lege eine Kategorie an, dann einen Artikel. Ich buche 100 ein und 30 aus — der Bestand steht auf 70. Buche ich mehr aus als vorhanden ist, lehnt das System es ab.

2 · Übergang Schlüsselsatz

Das Interessante ist nicht die App selbst — CRUD kann jeder. Interessant ist, wie ich sie gebaut habe und warum ich mich für bestimmte Lösungen entschieden habe.

3 · Domäne ~1 min

Das System verwaltet den Lagerbestand: Artikel, Kategorien und Ein- und Ausgänge — für ein Unternehmen mit vielen Produkten.

4 · Vorgehensweise ~3 min · Diagramme zeigen

Ich habe nicht sofort losgecodet. Zuerst die fachliche Analyse, dann das Datenmodell, dann UML, dann die Architektur — erst danach Code.

  • Analyse: Entitäten vs. Attribute, User-Stories, Business-Regeln
  • Datenmodell: Tabellen, Schlüssel, Beziehungen (ER-Diagramm zeigen)
  • UML: Use-Case + Klassendiagramm zeigen
  • Architektur → Code → Validierung

5 · Kernentscheidung: Bestand wichtigste Story

Den Bestand speichere ich nicht als Spalte, sondern berechne ihn aus den Bewegungen. So kann er nie im Widerspruch zur Historie stehen. Ich tausche etwas Lesegeschwindigkeit gegen Korrektheit.

  • Abwägung: Performance vs. Konsistenz vs. Redundanz → Konsistenz gewinnt

6 · Kernthema: Sicherheit

Alle Abfragen nutzen Prepared Statements gegen SQL-Injection. Passwörter speichere ich nur als Hash, nie im Klartext. Eingaben validiere ich serverseitig — man darf dem Client nie vertrauen. Rechte prüfe ich serverseitig, nicht nur in der Oberfläche.

7 · Architektur & Regel

Die App ist in Schichten getrennt: Model, Repository, Controller, Template — jede mit genau einer Aufgabe. Das macht den Code wartbar.

Die Regel „kein negativer Bestand" kommt aus der Analyse, steht im Aktivitätsdiagramm und wird im Controller durchgesetzt.

  • Docker: reproduzierbare Umgebung, auf jedem Rechner gleich

8 · Reflexion ~1 min

Ich hatte ein Dashboard gebaut, es aber wieder entfernt — es brachte keinen echten Mehrwert. Für den Produktivbetrieb würde ich den Seed-Admin entfernen und eine DB-Verbindungs-Wiederholung einbauen.

Unbedingt erwähnen ✓

  • Analyse vor dem Code
  • Bestand abgeleitet — mit Abwägung
  • Prepared Statements · Passwort-Hash · Server-Validierung · Rollen
  • Business-Regel: Analyse → Diagramm → Code
  • Schichten / Wartbarkeit
  • Docker · Scope bewusst gekürzt (Dashboard)

Q&A — vorbereitet

Warum abgeleiteter statt gespeicherter Bestand?

Einzige Wahrheitsquelle — kann nie von der Historie abweichen. Nachteil: langsamer bei sehr vielen Bewegungen; dann würde man cachen.

Warum ENUM für type, aber Tabelle für Kategorie?

type = kleine feste Menge ohne eigene Daten (in/out) → ENUM. Kategorien haben eigene Daten und werden zur Laufzeit verwaltet → Tabelle.

Warum Prepared Statements?

Trennen Daten von SQL-Code — Eingaben können nie als Befehl ausgeführt werden.

Warum kein Klartext-Passwort?

Bei einem Datenleck wären alle sofort sichtbar. Hash ist einwegs; password_verify prüft ohne Entschlüsseln.

Wo liegt der Fremdschlüssel?

Auf der „viele"-Seite — ein FK ist ein einzelner Wert und zeigt auf sein eines Elternteil.
